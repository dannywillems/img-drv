# The mathematics, and what it forces

This is not decoration. Every architectural constraint in this repository is a
consequence of one of the results below, and if a design choice cannot be
traced back to one of them it is a preference and should be labelled as such.

## 1. Why finite products are enough

A build description is first-order data: strings, paths, lists, records, and
references to other derivations. The operations are first-order maps between
products of those.

That makes the signature a multi-sorted **algebraic theory** in the sense of
Lawvere: a category with finite products, whose models are exactly the
finite-product-preserving functors out of it.

> **A Lawvere theory has a model in ANY cartesian category.**

Every typed language worth targeting has finite products, which is to say
records and tuples. So an eDSL restricted to a first-order algebraic signature
embeds in all of them **by construction**. No higher-kinded types, no type
classes, no row polymorphism, no dependent types are required. Those buy
ergonomics and static checking; they do not buy expressiveness here.

**Consequence for this repo:** the signature in `docs/spec/` may only use
products, finite sums, lists and primitives. Any proposed extension that needs
more than that is a red flag, and Go is the place it will show up first (see
`README.md`).

## 2. The common surface language is forced, not designed

Given a signature `S`, the free `S`-algebra `T(S)`, the term algebra, has this
universal property: any interpretation of the primitives into any `S`-algebra
`A` extends **uniquely** to a homomorphism `T(S) -> A`.

Read off three facts:

1. each host language's eDSL is a **presentation** of one and the same
   structure;
2. the interchange format **is** the initial object, serialized;
3. every backend (hash it, build it, diff it, plan it, visualize it) is an
   `S`-algebra, and each therefore determines exactly one homomorphism out of
   the term.

Initial objects are unique up to isomorphism. That is why AWS CDK (to
CloudFormation), cdktf (to Terraform JSON) and Pulumi (to its own protocol) all
converged independently on "typed eDSL in N languages, one JSON-shaped IR".
They were rediscovering the universal property.

**Consequence for this repo:** the valuable artifact is the IR and its
serialization, not the eDSLs. The eDSLs are cheap and interchangeable precisely
because the initial object is unique. Spend the care on `docs/spec/`.

## 3. The encoding must be initial, not tagless-final

Tagless-final (Carette, Kiselyov, Shan) encodes an eDSL as a family of
overloaded operations interpreted directly into the host language. It is the
usual advice for embedding a DSL, and it is **wrong here**.

Content-addressing hashes the DESCRIPTION. A final encoding interprets and
discards, leaving no syntactic object to hash. So the term must be reified as
data first and interpreted second. Nix's `.drv` is exactly that reified term.

A tagless-final layer is permissible as sugar, provided one of its
interpretations is "build the initial term".

**Consequence for this repo:** every eDSL builds a value and returns it. No
eDSL may perform I/O, and none may interpret directly.

## 4. Reproducibility is the well-definedness of a quotient

Reproducibility means the map `terms -> outputs` factors through `terms/~`,
where `~` is the congruence generated by the intended equalities: argument
order, path normalization, string encoding, map and set ordering. Content
addressing picks a representative of each equivalence class and hashes it.

That factorization is well defined **only if** normalization is confluent and
terminating. That is Newman's lemma: local confluence plus termination gives
confluence, hence unique normal forms.

If it fails, the Go eDSL and the OCaml eDSL serialize the same intent
differently, hash differently, and cache sharing dies silently, which was the
entire point of the exercise.

**Consequence for this repo:** canonical serialization is not a detail, it is
the proof obligation. The rules (key ordering, integer encoding, string
normalization, no floats) belong in the spec, and the decisive conformance test
is that three independent implementations emit BYTE-IDENTICAL output for the
same intent. That test is the project's reason to exist.

## 5. The scope spans two different algebras, and they must not be merged

Anything that grows toward "provision machines" contains two mathematically
distinct layers. Conflating them is the classic failure of infrastructure
tools.

**Artifact layer.** Build an image, a derivation, an answer file. Pure,
deterministic, cacheable. A free algebra on a signature. Evaluation order does
not matter, because the rewriting is confluent, which is exactly what makes it
content-addressable.

**Effect layer.** Boot a machine, write a disk, converge a running system.
Objects are machine states, morphisms are provisioning steps. The correctness
law is **idempotence**, `f . f = f`, an idempotent endomorphism, and a converged
machine is a **fixed point**, reached by Kleene iteration of a monotone map on
a lattice of states. Effects do not commute, so there is no confluence, no
normal form, and nothing to hash.

One sentence explains the whole tool landscape: **Nix is cacheable because its
layer is confluent; Ansible is not cacheable because its layer is not.**

**Consequence for this repo:** `img-drv` is an ARTIFACT-layer project. It emits
descriptions. It does not converge machines, and it must not grow an `apply`
verb. If an effect layer is ever wanted it gets a separate, deliberately small
interface whose guarantee is a tested idempotence rather than a hash.

## 6. The module system, and where its algebra actually bends

NixOS modules are functions of the final configuration, and evaluation ties a
**knot**. Option types supply the merge and priorities select which definitions
survive.

For module ORDER not to matter, that merge must be commutative, associative and
idempotent: a **join-semilattice**. That much is a law and it is
property-testable. An earlier version of this section then blamed the priority
machinery for breaking it. That was wrong in three ways, and the corrections are
sharper than the original claim.

### Priorities preserve the laws; the LIST types break them

Model a definition as a pair `(p, v)`. The merge keeps only the definitions at
the MINIMUM priority and applies the type's merge to those, which is the
**lexicographic product of a min-semilattice on priority with the value
semilattice**:

```
(50,a) join (100,b)  = (50,a)
(100,b) join (100,c) = (100, merge{b,c})
```

Commutative and associative whenever the underlying merge is, so `mkForce` is
not lawless: it is a level in a graded semilattice.

What genuinely leaves the semilattice is the TYPES:

- `listOf` merges by **concatenation**: associative, not commutative, not
  idempotent. `mkOrder`/`mkBefore`/`mkAfter` exist to give an explicit sort key
  so the non-commutativity is controllable rather than dependent on evaluation
  order. The honest structure is an **ordered monoid**, not a semilattice.
- `mergeOneOption` (`types.unique`) errors on two definitions even when they are
  EQUAL, so `x join x` is bottom. Not idempotent.
- Scalars (`bool`, `int`, `float`, `str`) use `mergeEqualOption`: all
  definitions must agree. That IS a semilattice, the **flat lattice** on the
  value set with a top element "conflict".

So the accurate statement is: a join-semilattice **per option type**, and
exactly the concatenating and unique types fall out of it.

### The merge is n-ary and does NOT decompose into binary merges

This is the sharpest point, and the one an implementer will get wrong. Merging
`{(50,a), (100,b)}` yields `a`, and the result no longer carries a priority.
Merge that with `(100,c)` and you get `merge{a,c}`, where merging all three at
once gives `a`:

```
merge(A union B)  !=  merge({merge A, merge B})
```

The definition multiset is the free commutative monoid on definitions and the
merge is a map out of it; the laws say exactly that this map is well defined on
the quotient. It is **not a fold**, and any implementation that folds pairwise
gets `mkForce` wrong.

### The knot is laziness, not Kleene iteration

Nix computes `fix f = let x = f x in x` and relies on laziness.
Well-definedness comes from the value dependency graph being acyclic and
productive, not from monotonicity on a cpo with an ascending chain condition.
Knaster-Tarski gives existence for monotone maps; Nix gives you "infinite
recursion encountered". Conflating the two would overclaim, and a strict-language
implementation gets to choose which it actually wants (see `PLAN.md` phase 3).

### Cross-field connection

A join-semilattice of states with monotone updates and merge = join is exactly
the **CvRDT convergence condition**. The module system is almost a state-based
CRDT, and `listOf` is precisely where it stops being one. That is why module
order sometimes matters in NixOS and usually does not.

## 7. Self-reference is avoided by FACTORING, not by a fixed point

A derivation's output paths are a hash of the derivation that contains them.
Written down naively that is

```
p = H(D(p))
```

an equation whose solution would be a hash of a text containing that very hash.
Nothing forces such a solution to exist, and iteration cannot find one, because
a hash function is built precisely to destroy the structure an iteration would
need. Every content-addressed system meets this problem, and it is worth being
explicit that Nix does not solve it. It arranges not to have it.

Let `pi` be the MASKING map that replaces each of a derivation's own output
paths by the empty string, in the outputs list and in the env entries whose KEY
is an output name. Let `f` compute paths from a masked derivation. The
definition is

```
outputs(d) = f(pi(d))
```

Since the right-hand side depends on `d` only through `pi(d)`, it is constant on
the fibres of `pi`, so it factors through the quotient `D/ker(pi)`. That is the
universal property of a quotient, and the payoff is concrete: computing output
paths is a TOTAL function evaluated in one pass, not a search for a fixed point.

Three consequences, and the repository depends on all three.

1. **Verification exists at all.** Because the paths are a FUNCTION of the
   masked form, the equation `recorded outputs == f(pi(d))` is a checkable
   claim rather than a definition. Anyone can recompute and compare, which is
   `Corpus.verify` (`impl/python/src/img_drv/corpus.py:139`) reproducing 1259
   of 1259 real output paths. A genuinely self-referential hash would admit no
   such check, and with it would go the ability to know a build's address
   before building it.
2. **The factorization is deliberately BROKEN in exactly one place.** A
   derivation's own paths go through `pi`; the hash by which it is known as
   someone else's INPUT does not, because there the paths are already known and
   are part of what identifies it (`store.py:155`, `corpus.py:99`). Applying
   `pi` in both places leaves every fixed-output derivation's own path correct
   and everything downstream of it wrong, which is invisible until something
   depends on a fetch.
3. **`pi` masks by KEY, not by value.** It blanks an env entry whose key is an
   output name, never an output path that merely occurs inside some other value
   (`aterm.py:245`). A textual substitution cannot draw that distinction, which
   is why a regex implementation passed 12 of 12 hand-written examples and
   failed 323 of 403 real ones.

Contrast with section 5. The effect layer's convergence is a GENUINE fixed
point, reached by Kleene iteration of a monotone map. The artifact layer looks
like one and is not, and recognizing that is exactly what makes it computable
in a single pass.

**Consequence for this repo:** an eDSL builds the derivation with its output
paths blank, computes them from the masked form, and substitutes them in
(`impl/python/src/img_drv/edsl.py:369`). An implementation that iterates toward
a path assignment, or that reaches one by any other route, is doing something
this specification does not describe.
