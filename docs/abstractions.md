# Abstractions

A running record of the structure each non-trivial piece of this repository
realizes: the carrier, the operations, the laws, where the code implements it,
and where those laws are actually TESTED.

This is not `theory.md`. That file holds the few normative results that FORCE
design constraints, and it is meant to stay small and stable. This file is a
LOG: one entry per feature worth naming, appended as work lands, so the map
from code to structure is recoverable later without re-deriving it.

Why keep it at all. A named structure is a SPECIFICATION, and every law it
obeys is a property the code must satisfy. The entries below have already paid
for themselves twice: the factorization in entry 3 is what makes verification
possible rather than merely convenient, and entry 4 is a bug that satisfied
every law the written spec stated and was still wrong.

Rules for an entry:

- Name the WEAKEST structure that truly fits, then say what richer object it
  sits inside. Do not force an analogy; if something is plumbing, say so in one
  line and skip it.
- Give the map from code to structure with `file:line`, checked, not
  remembered.
- State where each law is tested, and mark laws that are NOT tested as such.
  A law nobody checks is a comment.
- Record where the implementation deviates from the ideal object, and why.
- Mark our own interpretations as "our framing" rather than implying a source.

## 1. Canonical serialization is a normal form, and the form is Nix's

**Date:** 2026-08-01, revised 2026-08-02.

**Structure.** A normalization function `canonical` on derivations, together
with the serialization `unparse`. Together they pick one representative from
each class of the congruence generated by the orderings that carry no meaning:
env is a map, `inputDrvs` and `inputSrcs` are sets, `args` is a genuine list.
This is the quotient of `theory.md` section 4, made concrete.

**Carrier and operations.** `Derivation` (`derivation.py:75`), with
`canonical : Derivation -> Derivation` (`edsl.py:321`) and
`unparse : Derivation -> str` (`aterm.py:188`).

**Laws, and where they are tested.**

| law | scope | test |
| --- | --- | --- |
| `parse . unparse = id` | every derivation | `test_aterm.py:79` |
| `unparse . parse = id` | canonical text only | `test_golden.py:33`, and `make corpus` |
| `canonical . canonical = canonical` | every derivation | `test_edsl_laws.py:270` |
| `canonical = id` | every derivation real Nix emits | `test_edsl.py:388`, `make canonical-check` |

**The one that matters.** The last row is what makes the form CANONICAL rather
than merely ours. It holds on 2516 of 2516 real derivations, and `make corpus`
now checks it on a fresh random nixpkgs sample on every CI run
(`scripts/fetch-corpus.sh`). Without it, "four implementations agree byte for
byte" would only mean the four agree with each other, which is not the claim.

**Deviation.** `canonical` deduplicates `inputSrcs` and each inner output-name
list. Nix has never been observed to emit a duplicate in either, so the
dedup is unreachable on real input; it is there so that a caller who supplies
one gets a canonical result rather than a non-canonical one.

**Not tested.** Confluence and termination of the normalization are argued
rather than checked. Both are immediate here because `canonical` is a single
pass of total sorts rather than a rewriting system, so Newman's lemma is not
actually needed; `theory.md` section 4 invokes it for the general case.

## 2. The closure input-hash is a fold over a well-founded DAG

**Date:** 2026-08-01, corrected 2026-08-02.

**Structure.** `Corpus.input_hash` (`corpus.py:99`) is defined by structural
recursion over the derivation DAG: a derivation's hash is a function of its own
text with each input's store path replaced by that input's hash. Because the
DAG is finite and acyclic, the recursion is WELL-FOUNDED, which is what makes
the definition pick out exactly one function. That uniqueness is the reason
every conforming implementation in any language must produce the same digests.

**Memoization is sound** because a derivation is an immutable value and its
hash depends only on its transitive inputs. A 226-derivation closure hashes the
same bootstrap tools hundreds of times; the memo table (`corpus.py:84`) makes
verification linear in edges rather than exponential in depth.

**Correction, kept deliberately.** This module's docstring previously called it
"the unique homomorphism from the derivation DAG into the monoid of digests
induced by the hash function". That was an over-claim: there is no monoid, since
digests carry no associative operation under which the map would be a
homomorphism. The honest statement is the one above, unique by well-founded
recursion rather than by a universal property. The weaker claim is the true one,
and it still gives everything the project needs.

**Laws, and where they are tested.**

| law | test |
| --- | --- |
| hashing is a function (same input, same answer) | `test_golden.py:51` |
| recomputed output paths equal recorded ones | `test_golden.py:43`, `make corpus`, `make differential` |

## 3. Output paths factor through masking, so there is no fixed point to solve

**Date:** 2026-08-02. Written up normatively as `theory.md` section 7.

**Structure.** The apparent self-reference `p = H(D(p))` is avoided by defining
`outputs(d) = f(pi(d))`, where `pi` blanks the derivation's own output paths.
The right-hand side depends on `d` only through `pi(d)`, so it is constant on
the fibres of `pi` and factors through the quotient `D/ker(pi)`. Computing
paths is therefore a total, one-pass function, not a search.

**Map to code.** `pi` is `unparse(..., mask_outputs=True)` (`aterm.py:188`);
`f` is `output_paths` (`store.py:179`); the eDSL ties the knot by building with
blank paths, computing, and substituting (`edsl.py:369`).

**What the structure PREDICTS, and the code confirms.**

- Verification is possible: `recorded == f(pi(d))` is a checkable equation, not
  a definition. `Corpus.verify` (`corpus.py:139`), 1259 of 1259 real paths.
- The factorization must be broken for the input-hash, where paths are known
  and are part of the identity (`store.py:155`). Law:
  `input_hash != self_hash`, tested at `test_edsl_laws.py:322`.
- `pi` masks by KEY, never by value (`aterm.py:245`), tested at
  `test_aterm.py:110`.

**Deviation.** A fixed-output derivation does not use `f` at all: its identity
comes from the declared hash, so `pi` is irrelevant to it (`store.py:137`).
`r:sha256` deviates further still, taking the `source` kind with the declared
hash used directly. Exactly one derivation in a 226-derivation closure
exercised that.

**Contrast worth keeping.** The effect layer of `theory.md` section 5 has a
GENUINE fixed point, reached by Kleene iteration. This one only looks like one.
Telling the two apart is what makes this layer computable in a single pass, and
it is the sharpest statement of why the artifact layer is cacheable.

**Our framing.** The behaviour is Nix's; reading it as a factorization rather
than a fixed point is ours.

## 4. `outputs` is an Option, and the defaulted version is a NON-STANDARD MODEL

**Date:** 2026-08-02.

**Structure.** `Option [OutputName]`, a two-case finite sum
(`spec/signature.md`), NOT a list with a default. `None` and `Some ["out"]` are
distinguishable in the serialized bytes and therefore denote different
derivations with different store paths.

**How it was found, and why it is worth an entry.** The obvious implementation
defaults `outputs` to `["out"]`. That implementation satisfies every law the
written specification stated at the time, and is still wrong: Nix emits the
`outputs` env variable exactly when the caller DECLARED the attribute. In a
2516-derivation sample, 96 single-output derivations omit it and 605 emit
`("outputs","out")` (`spec/canonical.md` section 1.7). A defaulted model can
express one of those two, never both, whichever convention it picks.

This is a clean instance of the failure mode worth hunting for by default:
**an implementation satisfying every axiom you wrote down, and not the theory
you meant.** The remedy is to add the axiom that excludes it, which here is
simply that the option is observable, now invariant 7 of `spec/signature.md`.

Generalization worth reusing: whenever an API offers a default, ask whether
"not supplied" and "supplied equal to the default" are distinguishable
downstream. If they are, the parameter is an Option and the default is a lie.

**Laws, and where they are tested.**

| law | test |
| --- | --- |
| `None` and `Some ["out"]` differ in bytes and in path, for every intent | `test_edsl_laws.py:297` |
| the `outputs` variable keeps DECLARATION order while the outputs list is sorted | `test_edsl.py:206`, and 575 of 1197 real cases differ |

**Our framing.** The measurements are Nix's behaviour; the model-theoretic
reading is ours.

## 5. Well-definedness of the eDSL is what makes portability testable

**Date:** 2026-08-02.

**Structure.** Serialization must be a function of the INTENT, not of how the
intent was written down. Formally the eDSL's `derivation` is constant on the
classes of the congruence that permutes an unordered argument: the `env`
mapping and the `input_drvs` collection.

**Why it is load-bearing rather than tidy.** Python, Go, OCaml and Rust will
never agree on the iteration order of a mapping. If order leaked into the
bytes, byte-identical output across four implementations would be unreachable
BY CONSTRUCTION, and the thesis would fail for a reason that has nothing to do
with the thesis. These are therefore the first laws to port to each new
implementation.

**Laws, and where they are tested.** All are property-tested over generated
intents with Hypothesis (`test_edsl_laws.py`), not over examples.

| law | test |
| --- | --- |
| `env` insertion order is not observable | `test_edsl_laws.py:201` |
| `input_drvs` order is not observable | `test_edsl_laws.py:218` |
| naming one dependency twice is naming it once | `test_edsl_laws.py:234` |
| describing the same intent twice gives the same bytes | `test_edsl_laws.py:186` |
| `path == drv_path(aterm, name)` | `test_edsl_laws.py:277` |
| a described closure verifies like a real one | `test_edsl_laws.py:345` |

The last one closes the loop between the two halves of the library: a generated
DAG is described, written out, parsed back, and re-verified by the same code
that checks real nixpkgs closures, reaching the same answer by a different
route.

**Deviation.** `args` is deliberately NOT quotiented: there its order is the
meaning. Recording that as a deviation rather than an oversight is the point of
this column.

## 6. Two presentations of one theory, and what a stronger type system buys

**Date:** 2026-08-02, with the Rust port.

**Structure.** `theory.md` section 2: each host language's eDSL is a
PRESENTATION of one and the same initial object, and the interchange format is
that object serialized. Two presentations now exist, so the claim is testable
rather than asserted: `make conformance` has Python and Rust describe the same
ten intents and diffs the bytes three ways (against each other, and each
against what real Nix emitted).

The three-way diff is the part that matters. Two implementations agreeing on
the WRONG bytes would pass a two-way comparison; the golden files are what stop
"portable" from meaning "consistently mistaken".

**Result.** 10 intents, 2 implementations, byte-identical, including each
derivation's own `.drv` store path.

**The gate has teeth, checked rather than assumed.** Emitting the `outputs` env
variable in sorted order instead of declaration order (a one-line change, and
exactly the mistake `canonical.md` section 1.7 warns about) moves `multi`'s
store path from `v27a4...` to `hm669...`, and conformance fails naming Rust as
the implementation that stopped matching Nix. This repository has shipped a
`make` target that could never pass before, so a gate is not counted until it
has been seen to fail.

**What the second type system actually bought.** The typing table lives in
`impl/rust/README.md`; the pattern in it is worth stating here. Rust converts
three of Python's RUNTIME checks into compile-time impossibilities (the
newtype confusions, the hash algorithm, the ingestion mode) and one PROPERTY
TEST into a non-property (`env` is a `BTreeMap`, so there is no insertion order
for the bytes to depend on). What it converts none of is any invariant that
compares a value against COMPUTED data: outputs non-empty, names valid, a
fixed-output derivation having one output, and above all "the recorded paths
match this derivation's own hash". Those need a checker, not a type, in any
language.

The reversal is equally instructive. `Output::hash_algo` is a `String` and not
the `HashAlgo` enum, on purpose: parsing must be TOTAL over whatever real Nix
wrote, so the wire type stays permissive and strictness lives on the
construction side. A type system makes illegal states unrepresentable only
where YOU are the one constructing them.

**A bug the port found.** `base32` shifts a `u8` left by `8 - offset`, which is
a shift by 8 when `offset` is 0. Python is correct without a guard because its
integers are unbounded; in Rust that PANICS in debug and is silently masked to
a shift of 0 in RELEASE. `cargo build --release` was clean and `cargo test`
caught it. A release-only wrong answer inside a hash function is the worst
available failure mode, and porting is what surfaced it: one implementation
tested alone never would have.

**Deviation.** The two presentations are not identical in surface: `Build { ..
Default::default() }` rather than keyword arguments, `needs` rather than `ref`,
and no bare-`Drv` shorthand because the conversion can fail and `From` cannot.
Each is recorded in the Rust README with its cause. None of them is a
difference in the THEORY, which is the claim the conformance target actually
tests.

## 7. The falsification test came back negative, and what it measured

**Date:** 2026-08-02, with the Go port.

**What was being tested.** `theory.md` section 1 claims a first-order algebraic
signature has a model in ANY cartesian category, so an eDSL restricted to
products, finite sums, lists and primitives embeds in every typed language BY
CONSTRUCTION. Go is where that claim is cheapest to refute: no sum types, no
higher-kinded types, minimal generics. `README.md` states the bet explicitly,
that a clean Go embedding is the evidence and an ugly one is the refutation.

**Result: not refuted.** Every operation and every ordering rule in the
specification is expressible in Go, all ten golden intents reproduce Nix's bytes
including their own `.drv` store paths, and `make conformance` now shows three
implementations emitting identical bytes. Four generic functions were needed,
all of the weak "identical body for every type parameter" kind that Go's own
guidance sanctions. Nothing wanted a higher-kinded type or a type class.

**What it actually cost, which is the interesting part.** The cost is not in
EXPRESSIVENESS but in ENFORCEMENT and UNIFORMITY:

- a finite sum becomes a defined string type that accepts any string, so
  `HashAlgo("sha3")` compiles and a runtime `Valid()` check has to take over
  what Rust's `enum` and Python's `Literal` check statically;
- `Option` has no single spelling, so ONE concept in the other two
  implementations became THREE encodings here (a `Declared bool` discriminant,
  a nil pointer, and a zero-value sentinel);
- structural equality is hand-written, because a struct holding a slice is not
  comparable and `reflect.DeepEqual` would trade the type safety back.

**The one that would have been a real bug.** The obvious Go encoding for
`outputs` is `[]OutputName` with `nil` meaning "not declared". Go deliberately
makes nil and empty slices behave identically under `len`, `range` and
`append` — so the single distinction the BYTES depend on (entry 4) is the exact
distinction the language encourages you to ignore. The safe encoding is the
explicit discriminant, which is precisely the "struct with a discriminant plus a
constructor per case" that `AGENTS.md` predicts a sum type degrades into.
Everything else in the Go port cost lines; this one would have cost correctness.

**Where Go is BETTER, because reporting only costs would be dishonest.** Go
randomises map iteration on purpose, so forgetting to sort `env` before
serializing is a loudly flaky failure here and a silent one in Python (ordered
`dict`) and Rust (already-sorted `BTreeMap`). The law "describing the same
intent twice gives the same bytes" is therefore a real test of canonicalization
in Go and nearly vacuous in the other two. Go also DEFINES an over-wide shift as
zero, so the release-only `base32` bug from entry 6 cannot occur.

**The pattern, now visible across three languages.** A stronger type system
removes the checks on values you CONSTRUCT, and none of the checks on values you
COMPUTE. "Outputs non-empty", "name valid", and above all "the recorded paths
match this derivation's own hash" are runtime checks in Python, in Rust and in
Go, and always will be. That is not a language limitation; it is what
distinguishes a type from a verifier.

**Deviation.** The Go constructor is `Derive`, not `Derivation`, because
visibility is capitalisation and a package has one exported namespace, so the
type and its constructor collide. A "portable" API turns out not to be quite
portable in its SPELLING even where it is exactly portable in its meaning. The
full tally is in `impl/go/README.md`.

## 8. The other end of the axis: what a type can make unrepresentable

**Date:** 2026-08-02, with the OCaml port. All four implementations now exist.

**What was being tested.** Go asked whether the signature survives with almost
no type system. OCaml asks the opposite: how much of the specification can a
type system make UNREPRESENTABLE rather than merely checked? That is the axis
`README.md` says the four languages exist to span, and this is its far end.

**Result: exactly one row moves, and you can see it in the error type.** Every
other implementation validates the derivation name inside its constructor and
carries an `Invalid_name` case in its error enum. `Types.Name.t` is abstract
and its only constructor validates, so by the time `derive` is called an
invalid name is not a value that can exist, and `Edsl.error` has no such case.
An abstract type with a smart constructor moved an invariant from "checked at
construction" to "unrepresentable", and the shape of the error type is the
receipt.

Also worth keeping: three distinct identifier types come from ONE generative
functor applied three times, where Rust needs three newtype declarations and Go
three defined types.

**Result: the last two rows do not move, in any language.** "Outputs
non-empty" and above all "the recorded paths match this derivation's own hash"
are runtime checks in Python, Rust, Go AND OCaml. They compare a value against
COMPUTED data. This is now checked across the full typing axis rather than
conjectured from three points, and it sharpens entry 6's claim into something
stronger:

> A type system distinguishes what you CONSTRUCT. A verifier is still required
> for what you COMPUTE. No amount of type strength converts the second into the
> first.

The wire type shows the same boundary from the other side: `hash_algo` is a
`string` and not the variant in all four implementations, because parsing must
be TOTAL over whatever real Nix wrote. A type system makes illegal states
unrepresentable only where you are the one constructing them.

**A third language-specific trap, completing a pattern.** OCaml's `Digest` is
MD5 only, so this implementation writes its own SHA-256, and the first version
was wrong: a custom infix operator's precedence comes from its FIRST CHARACTER,
so `( &% ) = Int32.logand` sits at the level of `&&`, below `^%`, and
`a &% b ^% c` silently parses as `a &% (b ^% c)`. The FIPS 180-4 vectors caught
it on the first run.

Three ports, three traps, all in the same function:

| language | trap | how it failed |
| --- | --- | --- |
| Rust | `u8 << 8` panics in debug, is MASKED to `<< 0` in release | release-only wrong answer |
| Go | nil and empty slices behave alike, and the bytes depend on the difference | would have been silently wrong |
| OCaml | custom operator precedence comes from the first character | wrong parse tree, no warning |

None of these is about the signature. All three are in the layer where a value
is encoded rather than described, and each was caught by a gate that existed
before the code did. That is the argument for writing the vectors first.

**Conformance now spans the whole axis.** Ten intents, four implementations,
byte-identical to each other and to what real Nix emitted. The portability
claim is as well supported as this kind of claim can be, which is what
`PLAN.md` phase 2 set as its exit test.
